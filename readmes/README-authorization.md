# Authorization and Ticket Visibility

**Status:** FINALIZED  
**Security principle:** Backend authorization is mandatory. Frontend control visibility is not a security boundary.

The assignment explicitly requires ticket visibility and action permissions to be enforced for the authenticated user on the backend. Every list, detail, and action endpoint must apply these rules.

## 1. Role-specific visibility

### Client

A Client-role User can view all Tickets belonging to any Client mapped to that User through `UserClient`.

- Visibility is organization-level, not creator-level.
- All Client POCs mapped to the same Client can see the Client's Tickets, including Tickets created by other Client POCs or internal employees.
- If a Client user is mapped to multiple Clients, they can see Tickets belonging to those mapped Clients.
- A Client cannot see Tickets belonging to unrelated Clients.

Conceptual queryset:

```python
Ticket.objects.filter(
    Exists(
        UserClient.objects.filter(
            user=request.user,
            client_id=OuterRef("client_office__client_id"),
        )
    )
)
```

Use the actual related names generated by the implementation.

### Facility Manager

A Facility Manager can view every Ticket originating from Client Offices in the Properties they manage.

Visibility is independent of:

- Client occupying the Office;
- Ticket creator;
- Ticket's current Department;
- Ticket status (Open or Closed).

A Facility Manager must not see Tickets from Properties they do not manage, unless another independent role grants access.

Conceptual queryset:

```python
Ticket.objects.filter(
    client_office__property__facility_manager=request.user
)
```

One Property has one designated Facility Manager; one Facility Manager may manage multiple Properties.

### Department POC

A Department POC can view all Tickets whose **current Department** is the Department they represent.

Visibility is independent of Client, Property, and creator. It includes Open and Closed Tickets.

When a Ticket is forwarded from Technical to IT:

- the Technical POC loses visibility through the Department POC role;
- the IT POC gains visibility through the Department POC role;
- the Ticket's origin Department remains unchanged;
- a Facility Manager and associated Client users retain visibility through their own independent rules.

Conceptual queryset:

```python
Ticket.objects.filter(
    current_department__poc_user=request.user
)
```

### Worker

A Worker can view Tickets currently assigned to them **or previously assigned to them**.

- Current assignment grants operational visibility.
- Historical assignment preserves read-only visibility after reassignment or Department forwarding.
- Historical visibility remains after the Ticket is closed.
- A previously assigned Worker cannot perform Worker actions unless they are again the current active assignee and all stage/status preconditions are met.

Conceptual queryset:

```python
Ticket.objects.filter(
    Exists(
        TicketAssignment.objects.filter(
            ticket=OuterRef("pk"),
            worker=request.user,
        )
    )
)
```


### Creator visibility (all roles)

**Finalized decision (Phase 0 audit, B2).** Every user can also view the Tickets **they created**, in addition to their role-specific rule.

This keeps a creator's own Ticket visible after it is routed or forwarded to a Department they do not represent. Example: the Technical Department POC reports an "Internet not working" issue; the Ticket routes to IT, but the Technical POC can still open it. The wireframe shows every creator landing on their newly created Ticket. Workers cannot create Tickets, so this rule never applies to them.

### Combining the rules

A user's visible Tickets are: their role-specific rule **OR** Tickets they created (`created_by = request.user`).

Express each rule as an `Exists(...)` subquery or a direct foreign-key condition, combined with `Q(...) | Q(...)`. Do not join multi-valued relationships and call `.distinct()`: `Exists` never duplicates Ticket rows, keeps counts and pagination correct, and avoids PostgreSQL's restriction on `FOR UPDATE` with `DISTINCT` (see §5).

### Department membership representation

- The current Department POC is determined by `Ticket.current_department.poc_user`.
- Worker membership is determined through `DepartmentWorker` (`worker_id` unique), not through a `User.department_id` field.
- To find eligible Workers, query active `DepartmentWorker` rows for `ticket.current_department_id` and return their related Users.

## 2. Visibility and action permission are separate

A user being able to view a Ticket does not mean they can perform every action on it.

Every action endpoint must independently validate:

1. the authenticated user;
2. the user's role;
3. the user's relationship to the Client, Property, Department, or assignment;
4. the Ticket's current workflow stage and status;
5. action-specific input and business rules.

## 3. Permission matrix

| Capability | Client | Facility Manager | Department POC | Worker |
|---|---:|---:|---:|---:|
| View authorized Ticket | Yes | Yes | Yes | Yes, current or historical assignment |
| Create Ticket | Yes | Yes | Yes | No |
| Assign Worker | No | No | Yes, at permitted stage | No |
| Change Department | No | No | Yes, at permitted stage | No |
| Submit assessment | No | No | No | Current assigned Worker, at permitted stage |
| Mark Resolved | Yes, mapped Client user | Only on a Ticket they created | Only on a Ticket they created | No |
| View Activity | Yes, if Ticket visible | Yes, if Ticket visible | Yes, if Ticket visible | Yes, if Ticket visible |
| Add Comment | Yes, if Ticket visible | Yes, if Ticket visible | Yes, if Ticket visible | Yes, if Ticket visible |

Facility Managers have no handling CTA in the illustrated ticket detail flow, but they may create a Ticket from the internal-employee creation screen. On a Ticket they created they see Mark Resolved, as in the wireframe's internal-creation frame.

Department POCs may create Tickets, assign Workers, and change Department at the applicable stage. They have no additional handling CTA after Worker assessment in the assignment's defined flow.

Workers cannot create Tickets. Their only workflow action is submitting the assessment while currently assigned and eligible.

## 4. Action preconditions

### Create Ticket

Allowed roles: Client, Facility Manager, Department POC.

The creator must be mapped through `UserClient` to the selected Client. The selected Client Office must belong to that Client. The selected Office must also be within the creator's role-specific Office scope:

- `CLIENT`: any active Office belonging to a Client mapped to the user.
- `DEPARTMENT_POC`: any active Office belonging to a Client mapped to the user; Departments are organization-wide, not Property-specific.
- `FACILITY_MANAGER`: only active Offices belonging to a mapped Client **and** located in a Property where the user is the designated Facility Manager. The `UserClient` and managed-Property conditions are both required.

Client/Office selectors are conditional based on the user's mappings and the Office results the backend authorizes. A Facility Manager must not be able to create a Ticket for another manager's Property merely because the Client is mapped to them.

Form differences:

- Client-created Ticket: description is optional.
- Internal employee-created Ticket (Facility Manager or Department POC): description is required.
- Issue(s) are required for both.
- Floor selection is shown only when the selected Client Office has multiple mapped Floors, as specified in the wireframe.

### Assign Worker

Allowed role: current Department POC only.

Preconditions:

- Ticket workflow stage is `PENDING_TECHNICIAN_ASSIGNMENT`.
- Ticket status is `OPEN`.
- Request user is the designated POC of `Ticket.current_department`.
- Selected Worker has role `WORKER` and belongs to `Ticket.current_department`.
- No other active Worker assignment exists.

### Change Department

Allowed role: current Department POC only.

Preconditions:

- Ticket workflow stage is `PENDING_TECHNICIAN_ASSIGNMENT`.
- Ticket status is `OPEN`.
- Request user is the designated POC of `Ticket.current_department`.
- Destination Department exists and is active.
- Forwarding note is non-empty.

Update only `current_department_id`; preserve `origin_department_id`.

### Submit Assessment

Allowed role: currently assigned Worker only.

Preconditions:

- Ticket workflow stage is `PENDING_TECHNICIAN_ASSESSMENT`.
- Ticket status is `OPEN`.
- Request user owns the active TicketAssignment.
- No previous TicketAssessment exists.
- Outcome is one of the three allowed values.

### Mark Resolved

**Finalized decision (Phase 0 audit, B1).** Allowed users:

- a `CLIENT` user mapped through `UserClient` to the Client that owns the Ticket's Client Office; **or**
- the user who created the Ticket (any role).

This matches both wireframe frames: the Client sees Mark Resolved, and the Facility Manager who created a Ticket sees Mark Resolved on it, while a Facility Manager viewing a Client-created Ticket has no CTA.

Preconditions:

- Request user satisfies one of the two conditions above.
- Ticket is not already closed.
- Ticket is at one of the three supported workflow stages.

Set `status = CLOSED`, set `closed_by` and `closed_at`, end any active Worker assignment, and record Activity.

### Add Comment

Any user who currently has Ticket visibility may add a comment. Comment permission is independent of workflow-action permission. This includes a historically assigned Worker who retains read-only Ticket visibility.

## 5. Prevent IDOR and cross-tenant-style data leaks

Never retrieve a Ticket globally by ID and rely only on frontend routing or hidden buttons.

For list endpoints, scope the queryset to the authenticated User's permitted Tickets before filtering, searching, ordering, or pagination.

For detail and action endpoints, retrieve the Ticket through the same scoped queryset (or call a shared object-permission policy before accessing protected data). A user guessing another Ticket's ID must not receive its details or mutate it.

For state-changing actions, first confirm visibility through the scoped queryset, then lock the row with a **separate primary-key query**: `Ticket.objects.select_for_update().get(pk=ticket_id)`. Re-check every precondition after acquiring the lock. PostgreSQL rejects `FOR UPDATE` combined with `DISTINCT`, and locking through nullable joins requires `of=("self",)`; a plain primary-key lock avoids both problems.

Do not trust client-supplied values for:

- `created_by`;
- `origin_department`;
- `current_department`;
- `closed_by`;
- `assigned_by`;
- Worker identity for assessment submission.

Derive these from the authenticated user and server-side relationships.

## 6. API error semantics

Use a consistent error-response structure.

- `401 Unauthorized`: no valid authentication.
- `403 Forbidden`: the user can view the Ticket but is not allowed to perform the requested action.
- `404 Not Found`: the Ticket does not exist **or** is outside the user's visibility scope.
- `409 Conflict`: validly addressed Ticket, but its current state does not permit the requested transition.
- `400 Bad Request` / serializer validation response: malformed or invalid input.

**Finalized policy (Phase 0 audit, I4):** an inaccessible Ticket always returns `404`, on every Ticket detail, sub-resource, and action endpoint, so its existence is never revealed. The error envelope and codes are defined in `README-api-conventions.md`.

## 7. Authorization tests

At minimum, test:

1. A Client POC can see Tickets from their associated Client, including tickets created by another POC of that Client.
2. The Client cannot see another Client's Ticket.
3. A Facility Manager can see all Tickets from managed Properties, including different Clients and Departments, but not other Properties.
4. A Department POC sees Tickets currently in their Department; forwarding removes their Department-based visibility and grants the new POC visibility.
5. A Worker can see current and historical assignments, but a historical Worker cannot submit an assessment.
6. Guessing a Ticket ID does not bypass object-level authorization.
7. A Department POC who creates a Ticket routed to another Department can still view it, comment on it, and mark it resolved.
8. A mapped Client user and the Ticket's creator can mark it resolved; any other user who can view the Ticket receives `403`.

## 8. Assignment boundary

Do not add an Admin role or general user-management UI. Seeded accounts are sufficient. Registration, password reset, and user-management screens are not required by the assignment.
